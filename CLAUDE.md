## Read first

Before planning or coding, read [project_requirements.md](./project_requirements.md) (what to build, requirement IDs like `TAIL-3`, open questions `Q1`–`Q14`) and [guardrails.md](./guardrails.md) (how to plan and write code here), plus the current `Day_N.md` if one is attached (`Day_2.md` and `Day_3.md` are in the repo; `Day_1.md`, cited below and in `backend/README.md`, is not checked in). Guardrails is binding; the short version:

- Plans have three parts: goal + LLD, reasoning together (SOLID, tradeoffs, edge cases, fallbacks), second-brain check. Tables over prose; concise.
- LLD order: data classes → operation classes → pattern + SOLID principle per class → data structures. Don't write code before the LLD is agreed.
- No silent fallbacks: every fallback is raised in the plan first; default is to fail loudly with a specific exception. No bare `except`. Retries bounded and configured; log at WARNING+.
- Structured logs with a correlation id, `user_id` and entity id; never log CV/JD content, secrets or tokens.
- Give time/space complexity and cost per operation in plans.
- Reference requirement IDs (e.g. `PROF-4`, `TRUTH-2`) in plans, code comments and `Day_N.md`. Items marked ⚠ Q# are undecided — don't design past them without asking.

## Domain

Honne Careers: truthful JD-tailored CVs (P1, free), then Honne IQ (application tracker / knowledge layer, P2), built-in agents with a weekly report (P3), user-built custom agents (P4). Primary market India.

The product promise drives the design: **nothing invented**. Every skill, employer, title, date, metric and project in a generated CV must trace to a profile field, checked deterministically in Python after generation (TRUTH-1…4). LLM for judgment, deterministic Python for mechanics, JSON between machines, prose only at the user boundary — see the task-ownership table in project_requirements.md §8.

## Backend architecture

`api → services → (repositories, agents, truth, render, ingest, storage, policy) → domain`; `app/container.py` is the composition root (tests build it with fakes). Rules that are easy to break:
- **Tenancy is enforced twice.** Every DB call goes through `UnitOfWork` (`app/db`), which does `SET LOCAL ROLE authenticated` + JWT claims so RLS applies; repositories also filter by `user_id`. The login role `honne_backend` owns nothing. Another user's id → 404, never 403.
- **Client input shapes (`*In`) carry ids + text only.** `EditStamper` stamps `origin`/`locked` server-side (B5). Never accept origin/locked from a client.
- **The model never writes LaTeX or structural fields.** Agents return JSON; `TruthChecker` checks AI output against `FactSet` (item-scoped numbers, skills, dates, names); `ResumeMerger` drops edits to locked bullets and keeps originals for violations.
- **Skills in a full tailor (V4.1, 27 Oct 2026).** Scope `all`: no existing skill may be removed (`SKILL_REMOVED` keeps the category as it was); a skill may be **added** only if the user's own non-AI experience/project text in profile or resume shows it (`truth/facts.py: evidenced`; never the JD, never an unreviewed upload). A bad addition fails only itself (path `skills.<cat>[<name>]`). Additions are `origin=ai`; the CV page lets the user remove them. JD skills the CV doesn't show stay in `missing_skills` and reach Skills only via `POST /resumes/{id}/skills/confirm` (one click, this CV only, `origin=user`, only a listed suggestion; skills typed in the wizard also leave the list). Non-skill requirements (degree, years, spoken language) are `TailorOutput.gaps` → `resumes.jd_gaps` (migration `20261027000001`), shown read-only. `tailor_report` stays text-free: added/rejected skills are counts. Scope `experience_projects` never touches Skills.
- **`**bold**` is the only markup a bullet may carry** (`app/domain/markup.py`; frontend mirror `boldParts` in `cvModel.js`). The tailor agents bold 1–3 JD skills/metrics per bullet; `TruthChecker` rejects malformed bold, more than 3 spans, spans over 4 words, and bold on anything that isn't a user skill or one of the item's numbers (`Rule.BAD_BOLD`). Fact building, truth checks and the analyst read `plain(text)`; `rich()` (`app/render/latex.py`) emits `\textbf` and never adds or trims spaces at a span. Client bullets with malformed `**` get a 422.
- **PDF uploads are read in pypdf layout mode** (`PdfExtractor`, PROF-2). The default mode drops the space at a regular/bold switch and splits kerned pairs (`throughPython`, `T echnology`); uploads before 23 Oct stored exactly that. `tests/docs.kerned_bold_pdf` reproduces it, and the `latex` tests read every template's PDF back with pypdf layout + PyMuPDF. Stored text is repaired only by `scripts/repair_extraction_spacing.py` (dry-run → apply `--confirm <plan sha>` → rollback; whitespace-only, proven by the user's original file, `app/ingest/spacing_repair.py`), never by regex.
- **Templates (PDF-1, 28 Oct 2026)**: `TemplateRegistry` (`app/render/templates/__init__.py`) is the one list: `jake` (entry level, `jake.py`, output byte-identical to before) and `honne_professional` (experienced, `professional.py`, the CANAL+ reference's preamble and macros; Latin Modern **OpenType** instead of its T1/lmodern lines, because under Tectonic T1 ligatures extract as `ﬁ` and break ATS matching). Each entry has a `revision` and a `default_order`. A resume stores `template` + `section_order` (null = default; every `SectionKey` once, `app/domain/layout.py`), set by `PATCH /resumes/{id}/layout` (no AI, content untouched). The PDF cache key is `pdf_render_key` = sha256(content_hash, template, revision, order) (`core/hashing.py: render_key`); `TemplateRegistry.pdf_is_current` is the only freshness check (PdfService, ApplicationRecorder, `pdf.up_to_date`). An unknown stored template raises `RenderFailed(unknown_template)`, never falls back. **Add a template** = one renderer module + one registry entry; the DB checks only the id's shape, and `docker/warm_cache.py` / `smoke_compile.py` compile every registered template. **Bump `revision`** whenever a template's output changes. Renderers print sections in the given order and employers in stored order. `certifications` (name, issuer?, date?; typed by the user, AI never writes them) render only when present.
- **Agents are config** (`backend/agents/*.yaml` + `backend/prompts/`). `AgentRunner` owns retries, untrusted-data wrapping and the `agent_runs` record. Add an agent by adding files, not code.
- **No transaction is held across an LLM call, compile or storage call.** Services: short UoW → slow call → short UoW with optimistic concurrency.
- Never log CV/JD text (or Database notes); `tests/integration/test_logging_privacy.py` enforces it.
- **Application Database retention** (Day 2): rows keep only `last_sent_at`; `APPLICATION_RETENTION_DAYS` (40; `config.py` default, set in `render.yaml`) is the one place the number lives. Every user-facing read filters `last_sent_at >= cut-off` (`ApplicationRepository` takes the cut-off), and `RetentionJanitor` (daily, `JanitorLoop` in the container) deletes old rows: files first, then rows. The janitor is the only cross-tenant code: it runs as `honne_backend` without `SET ROLE` (`Database.maintenance_session`) and can only call the `app.janitor_*` SECURITY DEFINER functions, which refuse a cut-off newer than 1 day. Storage deletes across users go through `StorageAdmin` (service-role key, application-PDF paths only).
- **Chat agents** (Day 3, `app/agents/chat/`): user-made agents are rows (`chat_agents` identity + immutable `chat_agent_versions`, as in Dust), built-ins are files (`backend/agents/chat/*.yaml` + `backend/prompts/chat/`); both become an `AgentSpec` and run through one `ChatAgentRunner` → `TurnGraph` (LangGraph: model ↔ tools nodes; Gemini function calling through our provider port, mode ANY, `submit_answer` ends the turn). The system prompt is stacked by `ChatPromptBuilder`: platform rules first, then the user's guardrails, then instructions (user text escaped). Tools (`KnowledgeTools`) are **read-only**, bound to the user by closure (never a tool argument), filtered by the agent's knowledge grants, go through the existing services (RLS + retention cut-off), and return data wrapped as `untrusted_data` with a `ref` per row for `[n]` citations. A chat turn is a background job like the tailor job: `POST` → 202 with a `running` assistant message, steps written live, then `ok`/`failed`; one running turn per chat (partial unique index), stale after `chat_turn_timeout_s`; `TurnSlots` caps concurrent turns per process (429 `agents_busy`). Approved fallbacks F1–F4 are documented in `graph.py`.
- **Chat memory** (Day 3 §8): one chat, any agent, every agent sees the whole chat (Dust). Memory is `chat_messages` only; `history_of` gives the answering agent its own answers as model turns and other agents' answers as escaped `<other_agent>` notes. No @ → the last agent that answered, by identity (`Speaker`), never by handle. LangGraph's `AsyncPostgresSaver` (`AgentStateStore`, schema `agent_state`, own autocommit pool as `honne_backend`) holds only a running/failed turn's state, thread = assistant message id, so Retry resumes; a DB trigger drops it when the turn is `ok` or deleted, the janitor sweeps orphans. Never run the saver's `setup()`: upgrading `langgraph-checkpoint-postgres` needs a new migration (startup checks the version). LangGraph runs with LangSmith auto-tracing off (`tracing_context(enabled=False)`).
- **Usage limits** (`backend/config/limits.yaml`, the only place the numbers live): beta = 3 "Tailor my CV" runs/day (`full_tailor`), 5 new AI chats/day (`chat_start`; each Try it message counts too), 2 custom agents per user, plus safety caps (chat answers, bullet rewrites, PDFs, analyses, uploads). `LimitsConfig.load` validates it at startup (every plan must list every action; bad file → app won't start). Services call `QuotaGuard.consume(uow, user_id, DailyAction.X)` / `total_limit(...)`; it asks a `LimitPolicy` (`ConfiguredLimitPolicy`) for the plan's limits. Everyone gets `default_plan` while `use_account_plan: false`; later plans = add `free`/`plus`/`pro`/`pro_plus` blocks + flip the switch, no code change. `GET /me/usage` feeds the Settings "Beta limits" panel. UI text never mentions prices or paid plans. Tests use `tests/limits_test.yaml` (generous); `beta_api` fixture uses the real file.
- **Tracing** (`app/agents/tracing.py`): `Tracer` port, `LangSmithTracer` when `LANGSMITH_TRACING=true` (needs `LANGSMITH_API_KEY`, else startup fails), `NoopTracer` otherwise. One span per agent run, nested under `tailor_job` / `bullet_tailor_job`. Metadata only: never put CV/JD/model text in a span, and a failed span records only the exception class.

## AI agents and system prompts

One agent per AI task, no orchestration (Day_1 A2 #2). Each is a YAML config plus a Markdown system prompt; the model returns JSON only, validated against the agent's schema, then checked by `TruthChecker` where it writes CV text.

| Agent | Used by | Tier | Config | System prompt |
|---|---|---|---|---|
| `cv_tailor` | "Tailor my CV" job (`POST /resumes/{id}/tailor`) | strong | `backend/agents/cv_tailor.yaml` | `backend/prompts/cv_tailor/v4.md` (adapted `cv-jd-tailoring` skill, B4; v2 bolds keywords; v3 adapts to `career_stage`, TAIL-8; v4 keeps every skill, adds evidenced ones, splits `gaps` from `missing_skills`) |
| `bullet_tailor` | Wizard "Tailor to JD" on one bullet | strong | `backend/agents/bullet_tailor.yaml` | `backend/prompts/bullet_tailor/v3.md` (v2 bolds keywords; v3 adapts to `career_stage`) |
| `cv_parser` | CV upload / LaTeX paste → pre-fill | light | `backend/agents/cv_parser.yaml` | `backend/prompts/cv_parser/v2.md` (v2 adds spoken languages) |
| `cv_analyst` | "Start analysis" (judgments + evidence; Python computes the %) | light | `backend/agents/cv_analyst.yaml` | `backend/prompts/cv_analyst/v1.md` |

- **Edit a prompt:** change the Markdown file; it is sent verbatim as the system prompt. Keep the JSON fields it describes in line with the schemas in `app/domain/tailoring.py` / `analysis.py`, or replies fail validation (`llm_output_invalid`).
- **Version a prompt:** add `v2.md`, point the YAML's `instructions` at it and bump `version`; every run records the agent version in `agent_runs`.
- **Don't** add prompt-injection boilerplate (`AgentRunner` already wraps JD/CV text as untrusted data) or rely on the prompt for truthfulness (TRUTH-2 is checked in Python).
- Tiers map to models through `LLM_STRONG` / `LLM_LIGHT` (`render.yaml`, `.env`): Gemini 3.8 Flash (strong) / 3.5 Flash-Lite (light) today. Per-agent `temperature`, `max_output_tokens`, `timeout_s`, `max_retries` live in the YAML.
- CI never calls a model: tests script replies with `FakeProvider`, so real-model output quality (parsing, tailoring) is checked by hand on the deployed app.

**Chat agents (Day 3)** are a separate mechanism: multi-turn, tool-calling, prose answers (Markdown-lite with `[n]` cites + optional drafts), not one-shot JSON. Built-ins (strong tier, settings `AGENT_*` for timeout/retries/temperature):

User agents' instructions/guardrails are never logged; `agent_runs.agent_id` is `builtin:<handle>` or `custom:<agent id>` (`custom:preview` for Try it), with `tool_calls`/`tool_names`.

Ported from the Claude Design canvas "Honne Careers Landing Page" and the "Honne" design system; mirrors the conventions of the sibling Honne AI frontend (Vite, react-router, lucide-react, `@/` → `src/` alias, inline style objects). Tailwind is deliberately not used — its preflight reset breaks the design's inline SVG icons.

Routes (`src/App.jsx`): `/` landing, `/login` sign in, `/auth/callback` (Google returns here), then inside `RequireAuth` + `AppShell` (collapsible `Sidebar` + page): `/resumes` dashboard, `/home` (start page after sign-in, dashboard from `Home.dc.html`: KPIs, paste a JD, latest applications, AI career team, insights (`src/data/home.js`, rules on the user's own rows), latest CVs, profile bar, chat bar → `/chat`; reads `GET /applications`, `/resumes`, `/agents`, `/profile`, each card loading/failing on its own), `/agents` (list: Chat/Edit/Delete, limit), `/agents/new` and `/agents/:id/edit` (builder + Try it drawer), `/chat` (new chat) and `/chat/:id` (Day 3), `/new/template` → `/new/mode` → `/new/jd` → `/new/details?resume=<id>` (wizard) or `/tailoring/:id` (returning user), `/cv/:id` "Your CV is ready", `/profile`, `/database` (application Database), `/settings`. A JD pasted on Home sets `draft.jdFromHome`, so setup goes `/new/template` → `/new/jd` (Mode skipped, JD pre-filled); every "New resume" entry calls `resetDraft`.

Auth (AUTH-1, beta = Google only):
- `src/services/supabaseClient.js` — the one supabase-js client (PKCE). Throws at load if `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are missing; no placeholder fallback.
- `src/services/authService.js` — `signInWithGoogle`, `completeSignIn`, `signOut`, `safeNext` (same-site paths only), typed `AuthError`. The post-login path lives in sessionStorage so `redirectTo` is always exactly `<origin>/auth/callback` (must be in Supabase's redirect allowlist).
- `src/state/AuthProvider.jsx` + `auth.js` (`useAuth`) — mirrors `onAuthStateChange`; status `checking`/`authed`/`anon`. Tokens stay inside supabase-js; nothing is copied to localStorage.
- `src/components/RequireAuth.jsx` guards the app; `AuthCallbackPage` checks the session, then calls `GET /me` (creates the account row) before entering.
- `src/services/apiClient.js` — `apiRequest` for every backend call: Bearer token + `X-Correlation-Id`, backend error JSON → `ApiError` (`code`, `message`, `details`, `correlationId`), a 401 forgets the session. No retries. `errorText(e)` = the backend's user-facing message + reference.

Styling has two separate layers — keep them separate:
- **Landing** (`src/pages/landing/`), ported from the design's `Landing.dc.html` ("Landing v4 · Stripe direction"): `LandingPage.jsx` composes `sections/*` (each owns its own state, so the hero demo loop and the scroll-driven scenes re-render only themselves) and runs **Lenis** smooth scrolling (off with reduced motion); every in-page jump goes through `useScrollTo`/`useJump` (`landingHooks.js`). Data (all from the API; nothing seeded):

- `src/data/cvAdapter.js` — **the one adapter** between server shapes and UI shapes: `contentToDoc` derives each bullet's `status` from `origin`/`locked`/`tailor_state` (proposed → `review`, kept → `kept`, locked → `edited`); `docToContentIn`/`sectionPatch` send ids + text only (B5). - `src/hooks/useResource.js` — load + loading/error/reload for a screen (no fallback data). `src/hooks/useTailorJob.js` — polls `GET /resumes/{id}` (bounded: `src/config/limits.js`) and maps `job_step` to the steps shown (TAIL-3); `pollTailorJob` is the pure, tested loop.

- `src/components/Status.jsx` — `PageLoading` and `ErrorBanner` (message + reference + Retry/Reload).
- `src/data/applications.js` — the Database screen's adapter (`toApplicationList`, `toApplicationDetail`, `summaryOf`, `manualToRequest`, `patchRequest`) and helpers (outcome-only `STATUSES`, `REFERRALS` with null = "—", filters, board grouping). `src/services/applicationSaver.js` — save-on-download with the agreed retry: network/5xx only, bounded back-off (`RECORD_RETRY_*` in `limits.js`), then "pending" in localStorage, retried by `AppShell` on the next visit (`PENDING_SAVE_MAX_VISITS`).

### Frontend ↔ backend contract

`contracts/responses/*.json` are generated from the backend's real view functions (`UPDATE_CONTRACTS=1 pytest tests/contract`) and fed to the frontend adapter tests. `contracts/requests/*.json` are generated by the frontend's real adapter + `api.js` (`UPDATE_CONTRACTS=1 npm test`) and validated against the Pydantic input shapes by the backend (`extra="forbid"`, so origin/locked can never be sent). A shape change on either side fails the other side's CI until both are updated.

## Deploy

Both run on Render from `main` via `render.yaml` (Blueprint): the API as a Docker web service (`rootDir: backend`, Singapore, `/health` check, secrets in the `honne-careers-api-secrets` env group) and the frontend as a free Static Site (`rootDir: frontend`, SPA rewrite, CSP and security headers). Status (19 Oct 2026): Supabase project and migrations done; `main` holds the wired app and the Render Blueprint is the next step. Apply every file in `supabase/migrations/` to Supabase before the API deploy (the API reads `resumes.job_step`, `user_settings`, since Day 3 the chat tables, and it refuses to start without the `agent_state` schema from `20261024000001`). After the first deploy: add the static site URL to the API's `CORS_ORIGINS` and `<site>/auth/callback` to Supabase Auth's redirect allowlist; the API runs on Render's free plan for the beta (0.1 CPU, sleeps after 15 min idle, so LaTeX/parse timeouts are raised in `render.yaml`); move to Starter when real users arrive, Standard if the `docker` CI job's `tectonic_peak_rss_mb` needs 2 GB.

Supabase setup that breaks things silently (full list in `backend/README.md`): JWT signing keys must be **asymmetric** (the API rejects HS256, so every request fails with `auth_unavailable`); connect through the **session pooler** (IPv4) as `honne_backend.<project-ref>`; the `honne_backend` password is set by hand, never in a migration; keep the `app` schema out of the Data API's exposed schemas.

The frontend reads the API URL from `VITE_API_BASE_URL` (set in `render.yaml`; see `frontend/.env.example`) through `apiUrl()` in `src/services/apiConfig.js`, which throws in a production build if it's unset. Keep the static site's domain in the API's `CORS_ORIGINS` (never `*`; config rejects it). The CSP `connect-src` must list the API and `*.supabase.co`. The static site also needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (`sync: false` in `render.yaml`, set in the dashboard).
