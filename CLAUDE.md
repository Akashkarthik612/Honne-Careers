## Domain

Honne Careers: truthful JD-tailored CVs (P1, free), then Honne IQ (application tracker / knowledge layer, P2), built-in agents with a weekly report (P3), user-built custom agents (P4). Primary market India.

The product promise drives the design: **nothing invented**. Every skill, employer, title, date, metric and project in a generated CV must trace to a profile field, checked deterministically in Python after generation (TRUTH-1…4). LLM for judgment, deterministic Python for mechanics, JSON between machines, prose only at the user boundary — see the task-ownership table in project_requirements.md §8.

## Backend architecture

`api → services → (repositories, agents, truth, render, ingest, storage, policy) → domain`; `app/container.py` is the composition root (tests build it with fakes). Rules that are easy to break:
- **Tenancy is enforced twice.** Every DB call goes through `UnitOfWork` (`app/db`), which does `SET LOCAL ROLE authenticated` + JWT claims so RLS applies; repositories also filter by `user_id`. The login role `honne_backend` owns nothing. Another user's id → 404, never 403.
- **Client input shapes (`*In`) carry ids + text only.** `EditStamper` stamps `origin`/`locked` server-side (B5). Never accept origin/locked from a client.
- **The model never writes LaTeX or structural fields.** Agents return JSON; `TruthChecker` checks AI output against `FactSet` (item-scoped numbers, skills, dates, names); `ResumeMerger` drops edits to locked bullets and keeps originals for violations.
- **Agents are config** (`backend/agents/*.yaml` + `backend/prompts/`). `AgentRunner` owns retries, untrusted-data wrapping and the `agent_runs` record. Add an agent by adding files, not code.
- **No transaction is held across an LLM call, compile or storage call.** Services: short UoW → slow call → short UoW with optimistic concurrency.
- Never log CV/JD text; `tests/integration/test_logging_privacy.py` enforces it.

## AI agents and system prompts

One agent per AI task, no orchestration (Day_1 A2 #2). Each is a YAML config plus a Markdown system prompt; the model returns JSON only, validated against the agent's schema, then checked by `TruthChecker` where it writes CV text.

| Agent | Used by | Tier | Config | System prompt |
|---|---|---|---|---|
| `cv_tailor` | "Tailor my CV" job (`POST /resumes/{id}/tailor`) | strong | `backend/agents/cv_tailor.yaml` | `backend/prompts/cv_tailor/v1.md` (adapted `cv-jd-tailoring` skill, B4) |
| `bullet_tailor` | Wizard "Tailor to JD" on one bullet | strong | `backend/agents/bullet_tailor.yaml` | `backend/prompts/bullet_tailor/v1.md` |
| `cv_parser` | CV upload / LaTeX paste → pre-fill | light | `backend/agents/cv_parser.yaml` | `backend/prompts/cv_parser/v1.md` |
| `cv_analyst` | "Start analysis" (judgments + evidence; Python computes the %) | light | `backend/agents/cv_analyst.yaml` | `backend/prompts/cv_analyst/v1.md` |

- **Edit a prompt:** change the Markdown file; it is sent verbatim as the system prompt. Keep the JSON fields it describes in line with the schemas in `app/domain/tailoring.py` / `analysis.py`, or replies fail validation (`llm_output_invalid`).
- **Version a prompt:** add `v2.md`, point the YAML's `instructions` at it and bump `version`; every run records the agent version in `agent_runs`.
- **Don't** add prompt-injection boilerplate (`AgentRunner` already wraps JD/CV text as untrusted data) or rely on the prompt for truthfulness (TRUTH-2 is checked in Python).
- Tiers map to models through `LLM_STRONG` / `LLM_LIGHT` (`render.yaml`, `.env`): Gemini 2.5 Pro / Flash today. Per-agent `temperature`, `max_output_tokens`, `timeout_s`, `max_retries` live in the YAML.
- CI never calls a model: tests script replies with `FakeProvider`, so real-model output quality (parsing, tailoring) is checked by hand on the deployed app.

## Frontend architecture

Ported from the Claude Design canvas "Honne Careers Landing Page" and the "Honne" design system; mirrors the conventions of the sibling Honne AI frontend (Vite, react-router, lucide-react, `@/` → `src/` alias, inline style objects). Tailwind is deliberately not used — its preflight reset breaks the design's inline SVG icons.

Routes (`src/App.jsx`): `/` landing, `/login` sign in, `/auth/callback` (Google returns here), then inside `RequireAuth` + `AppShell` (collapsible `Sidebar` + page): `/resumes` dashboard, `/new/template` → `/new/mode` → `/new/jd` → `/new/details?resume=<id>` (wizard) or `/tailoring/:id` (returning user), `/cv/:id` "Your CV is ready", `/profile`, `/settings`. `/home` redirects to `/resumes`.

Auth (AUTH-1, beta = Google only):
- `src/services/supabaseClient.js` — the one supabase-js client (PKCE). Throws at load if `VITE_SUPABASE_URL`/`VITE_SUPABASE_ANON_KEY` are missing; no placeholder fallback.
- `src/services/authService.js` — `signInWithGoogle`, `completeSignIn`, `signOut`, `safeNext` (same-site paths only), typed `AuthError`. The post-login path lives in sessionStorage so `redirectTo` is always exactly `<origin>/auth/callback` (must be in Supabase's redirect allowlist).
- `src/state/AuthProvider.jsx` + `auth.js` (`useAuth`) — mirrors `onAuthStateChange`; status `checking`/`authed`/`anon`. Tokens stay inside supabase-js; nothing is copied to localStorage.
- `src/components/RequireAuth.jsx` guards the app; `AuthCallbackPage` checks the session, then calls `GET /me` (creates the account row) before entering.
- `src/services/apiClient.js` — `apiRequest` for every backend call: Bearer token + `X-Correlation-Id`, backend error JSON → `ApiError` (`code`, `message`, `details`, `correlationId`), a 401 forgets the session. No retries. `errorText(e)` = the backend's user-facing message + reference.

Styling has two separate layers — keep them separate:
- **Landing** (`src/pages/landing/`): `LandingView.jsx` is markup machine-converted from the design's `Main.dc.html`; `LandingPage.jsx` owns state (the rotating hero word). Its CSS in `landing.css` is scoped under `.hc-landing`, and its keyframes are prefixed `lp-`, because its class names (`.br`, `.rise`, `.dot`…) are generic. Hex colours are inline literals, as in the design.
- **App screens**: shared `hc-` prefixed classes and `--hc-*` design tokens in `src/index.css` (tokens come from the design system's `tokens.json`). Use the tokens rather than new hex values.

Data (all from the API; nothing seeded):
- `src/services/api.js` — one function per endpoint. Screens call these, never `fetch`. `getProfile()` resolves `null` for 404 `no_profile`; every other error throws.
- `src/data/cvAdapter.js` — **the one adapter** between server shapes and UI shapes: `contentToDoc` derives each bullet's `status` from `origin`/`locked`/`tailor_state` (proposed → `review`, kept → `kept`, locked → `edited`); `docToContentIn`/`sectionPatch` send ids + text only (B5). A `review` bullet is sent back unchanged so the server keeps the proposal. Also `validateDoc` (the API's required fields and http(s) links, shown on the field; never auto-fixed), `toResume`/`toSummary` (`state` = draft/tailoring/failed/ready; wizard_step `done` counts as ready), `toAnalysis`, `prefillToDoc`/`mergePrefill` (upload pre-fill fills only empty sections).
- `src/data/cvModel.js` — pure helpers between **profile** (facts, PROF-1), **doc** (per bullet `source` = fact, `text` = CV wording) and **cv** (what `CvDoc` renders).
- `src/hooks/useResource.js` — load + loading/error/reload for a screen (no fallback data). `src/hooks/useTailorJob.js` — polls `GET /resumes/{id}` (bounded: `src/config/limits.js`) and maps `job_step` to the steps shown (TAIL-3); `pollTailorJob` is the pure, tested loop.
- `src/state/` — `AppStoreProvider` holds only the new-resume draft (template, mode, JD text, company/role, upload pre-fill).
- `src/components/Status.jsx` — `PageLoading` and `ErrorBanner` (message + reference + Retry/Reload).
- `src/data/templatePreview.js` — illustrative content for the template picker's thumbnail only; never user data.

`src/components/CvDoc.jsx` renders a CV (`focus` highlights the section being edited; `CvThumb` is the scaled card thumbnail). Which templates are live comes from `GET /templates` (Jake only); the rest of `src/data/templates.js` shows as "Coming soon". Chat edits (CHAT-1…4) are not in this design and have no UI. Download builds the LaTeX PDF; the SAVE-1 application record is not built yet.

Every screen is wired; `mockApi.js`, the seeded store, `?user=new` and `?sim=` are gone.

| Screen | Endpoints |
|---|---|
| Dashboard | `GET /resumes` (includes `content` for thumbnails), `GET /profile`, `POST /resumes/{id}/duplicate`, `DELETE /resumes/{id}` |
| Template picker | `GET /templates` |
| Mode → scratch | `POST /resumes` (mode `scratch`) → wizard |
| JD page | `POST /uploads` (PDF/DOCX) or `POST /uploads/latex` (.tex read as text); `POST /resumes` + `PUT /resumes/{id}/jd` (with the user's company/role, SAVE-2); returning user then `POST /resumes/{id}/tailor` (202) → `/tailoring/:id` |
| Wizard | `GET /resumes/{id}`; leaving a step = `PATCH /resumes/{id}` for that section (409 → Reload); per bullet `/bullets/{bid}/tailor` (saves unsaved edits first), `/keep`, `/revert`; "Tailor all" = per-bullet calls, 3 at a time, plain/kept bullets only; Preview saves every section with `wizard_step=done` and, for a first-time user, `POST /resumes/{id}/save-to-profile` |
| Tailoring | polls `GET /resumes/{id}`; `job_step` reading → rewriting → checking; failed → Retry (`POST /tailor`) |
| CV ready | `GET /resumes/{id}`, `GET /settings`, `POST /resumes/{id}/pdf` (signed URL), Keep/Revert in "What changed", save to profile (respects `ask_before_save`) |
| Analysis | `POST /resumes/{id}/analysis` |
| Profile | `GET /profile`, `PUT /profile` with `expected_version` (409 → Reload) |
| Settings | `GET/PUT /settings` (display name, ask-before-save, product emails), `DELETE /me`, export = `GET /profile` + `GET /resumes` |

Backend additions for this (migration `20261019000001`): `resumes.job_step`, `user_settings` table (RLS forced), `PUT /jd` optional `company`/`role`, `GET/PUT /settings`. Truth fix (TRUTH-1): Keep keeps `original_text`; re-tailoring and save-to-profile use the fact behind an AI bullet (`truth/copying.py: fact_text`, raises `FactMissing` rather than guessing).

### Frontend ↔ backend contract

`contracts/responses/*.json` are generated from the backend's real view functions (`UPDATE_CONTRACTS=1 pytest tests/contract`) and fed to the frontend adapter tests. `contracts/requests/*.json` are generated by the frontend's real adapter + `api.js` (`UPDATE_CONTRACTS=1 npm test`) and validated against the Pydantic input shapes by the backend (`extra="forbid"`, so origin/locked can never be sent). A shape change on either side fails the other side's CI until both are updated.

## Deploy

Both run on Render from `main` via `render.yaml` (Blueprint): the API as a Docker web service (`rootDir: backend`, Singapore, `/health` check, secrets in the `honne-careers-api-secrets` env group) and the frontend as a free Static Site (`rootDir: frontend`, SPA rewrite, CSP and security headers). Status (19 Oct 2026): Supabase project and migrations done; `main` holds the wired app and the Render Blueprint is the next step. Apply every file in `supabase/migrations/` to Supabase before the API deploy (the API reads `resumes.job_step` and `user_settings`). After the first deploy: add the static site URL to the API's `CORS_ORIGINS` and `<site>/auth/callback` to Supabase Auth's redirect allowlist; the API runs on Render's free plan for the beta (0.1 CPU, sleeps after 15 min idle, so LaTeX/parse timeouts are raised in `render.yaml`); move to Starter when real users arrive, Standard if the `docker` CI job's `tectonic_peak_rss_mb` needs 2 GB.

The frontend reads the API URL from `VITE_API_BASE_URL` (set in `render.yaml`; see `frontend/.env.example`) through `apiUrl()` in `src/services/apiConfig.js`, which throws in a production build if it's unset. Keep the static site's domain in the API's `CORS_ORIGINS` (never `*`; config rejects it). The CSP `connect-src` must list the API and `*.supabase.co`. The static site also needs `VITE_SUPABASE_URL` and `VITE_SUPABASE_ANON_KEY` (`sync: false` in `render.yaml`, set in the dashboard).
